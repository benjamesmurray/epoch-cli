# dual-model-orchestration - Test Strategy

This document outlines the testing strategy for the dual-model-orchestration architecture, utilizing the newly implemented `prompt-logging-utility` and the `LogParserTool` to empirically verify the novel efficiency features of the system.

## 1. Verify Sequential "Baton Pass" Execution
**Goal:** Prove that `local-side` (Phase 1, Phase 3) and `local-main` (Phase 2) never overlap to avoid compute contention.
- **Execution:** 
  1. Start a chat session and trigger a complex prompt requiring external tool calls (to force Phase 1 pre-fetching and Phase 3 post-generation background tasks).
  2. Execute the `LogParserTool` against the generated log file.
- **Verification:** 
  - The parser must state: `Sequential execution verified. No overlap detected.`
  - The state-machine must confirm `Total sequential handoffs` is > 0.

## 2. Verify Task-Epoch Grouping
**Goal:** Prove that the architectural "cold restart" groups all events of a specific interaction into discrete, trackable epochs.
- **Execution:**
  1. Send 3 sequential prompts to the CLI.
  2. Inspect the raw `.log` file generated by `epochcli`.
- **Verification:**
  - `EnhancedModelExecutionEvent` logs for each interaction must share the exact same `epochId` across Phase 1, Phase 2, and Phase 3.
  - The `epochId` must change for each distinct prompt/task submitted by the user.

## 3. Telemetry: Verify TOON Optimizations & TTFT
**Goal:** Empirically verify that the Token-Oriented Object Notation (TOON) and "Zero-Fluff" prompt rules are successfully reducing token usage and improving Time-to-First-Token (TTFT).
- **Execution:**
  1. Submit a prompt requesting project-map context and spec-cli context.
  2. Review the `END_GENERATE` log event for `Phase 2` (`local-main`).
- **Verification:**
  - The `metrics.promptTokens` count must be logged and demonstrably lower than equivalent raw markdown string injections.
  - The `metrics.ttftMs` must be logged and clearly measurable.
  - The `metrics.tps` (Tokens Per Second) must be tracked and output correctly.

## 4. Verify Positional Prompt Truncation
**Goal:** Prove the U-shaped attention partitioning by verifying Zone 1 (task data) and Zone 3 (fact repetition) are protected during massive context injection, while Zone 2 (middle context) is truncated.
- **Execution:**
  1. Submit a massive block of text as user input (or force an enormous `mcp-spec-cli` dump) that exceeds normal token bounds and triggers truncation logging.
  2. Inspect the `START_GENERATE` `payload` field in the logs.
- **Verification:**
  - The payload must contain the `Zone 1` initial system instructions.
  - The payload must contain the `Zone 3` final repetition instructions.
  - The middle of the payload must contain the explicit truncation marker: `[... X messages truncated (Zone 2) ...]`.

## 5. Verify JSON Sanitization (MoE Repair)
**Goal:** Prove that when the 26B `local-main` model fails at basic JSON syntax, the 4B `local-side` model successfully catches and repairs it.
- **Execution:**
  1. Temporarily patch `local-main` output to forcefully simulate a missing bracket or escaped character in a tool call JSON blob.
  2. Submit a prompt that triggers the tool.
  3. Execute the `LogParserTool`.
- **Verification:**
  - The tool execution must successfully complete despite the initial bad JSON.
  - The log parser must explicitly state: `JSON Repairs: 1` (or >0), verifying that the `END_GENERATE` event logged with `json_repaired: true` from `local-side`.

## 6. Verify Phase 3 Background Abortion
**Goal:** Prove that if a user submits a new prompt while Phase 3 (The Archivist) is still summarizing the previous task, the system instantly cancels the background worker to free up VRAM.
- **Execution:**
  1. Complete a complex turn. The moment Phase 2 finishes and Phase 3 starts, immediately send a new prompt.
- **Verification:**
  - The logs must show an `ERROR` or abort event for the Phase 3 `local-side` invocation due to the AbortSignal firing.
  - Phase 1 of the *new* epoch must immediately begin without delay.

## 7. End-to-End (E2E) Test Run: The "Roaster" Utility
**Goal:** Run a comprehensive, autonomous test that exercises the `mcp-spec-cli`, `project-map-cli`, and the dual-model architecture in a single, complex workflow, storing all artifacts for post-test analysis.

- **Test Definition:** 
  Instruct the Epoch CLI to autonomously design and build a TypeScript utility called "roaster" inside `.epochcli/tool/roaster`. The utility must query the `project-map-cli` for repository context, construct a prompt, and make an HTTP request to the local LLM (`http://localhost:8085/v1/chat/completions`) to write a "roast" blog article about the codebase. The utility must include a test suite (using `bun test`) and a README.

- **Execution:**
  Execute the helper script `/home/benmurray/Projects/cli/e2e_testing/run_roaster_e2e.sh`. This script will:
  1. Create a timestamped evidence directory.
  2. Clean up any existing `roaster` artifacts.
  3. Execute the Epoch CLI in autonomous (`one-shot`) mode with the prompt.
  4. Pipe all `stderr` and `stdout` logs directly into a `run.log` file within the timestamped directory.
  
- **Evidence Collection:**
  The `run_roaster_e2e.sh` script will automatically copy the generated evidence into the timestamped test directory:
  1. `run.log` - The raw Epoch CLI logs containing the `EnhancedModelExecutionEvent` telemetry.
  2. `roaster_source/` - A copy of the generated TypeScript codebase (from `.epochcli/tool/roaster`).
  3. `spec_artifacts/` - A copy of the spec documents generated by the agent (from `projects/completed/roaster`).
  4. `parser_results.txt` - The output of running `LogParserTool` against the `run.log`.
  
- **Post-Test Analysis:**
  An `E2E_Analysis_Report.md` will be generated inside the timestamped directory. It will evaluate:
  - **Tool Orchestration:** Did the agent correctly use `sc_init` (one-shot), `pm_query`, and file writing tools without hanging?
  - **Dual-Model Efficiency:** Did `LogParserTool` verify that the baton passes occurred successfully without overlap?
  - **Code Quality:** Does the generated TypeScript code compile? Are the tests passing? Did it successfully make the HTTP call to the local LLM?
